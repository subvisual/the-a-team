# Rubric — the gate checklist

One rubric powers both modes. In CREATE it's the **convergence condition** (grill until green). In
REVIEW it's the **diagnostic**. Show it to the user as you work, so "done" and "broken" are legible,
not a black box. Every gate traces to `theory.md`.

## Axis 1 — FORM (judge from the text alone)

A statement passes FORM only if all of these hold:

- [ ] **Progress, not action.** Fails the disqualifier: you *cannot* readily picture someone performing
      it. If you can visualize the action, it's a task/solution, not a job. (theory: disqualifier test)
- [ ] **No solution or feature named as the job.** The job is not "what the product does." Products are
      hired *for* the job. (principle 2)
- [ ] **Names what it replaces.** The wording implies the solution(s) being fired — the single most
      important wording test. (theory: how to describe)
- [ ] **No persona / demographics.** The job is in the situation and struggle, not in who the person is.
- [ ] **Not typed.** It is not labelled or carved into functional / emotional / social jobs.
- [ ] **Progress shape, either phrasing.** Reads as a progress statement in one of the two accepted
      forms — "Free me from [struggle], so I can [better me]" OR "When [situation], I want to [progress],
      so I can [outcome]". Both are valid JTBDs. The skill's **default delivered form is the `When…`
      house format**; still draft/check in the "Free me from…" form to guarantee the `I want to…` clause
      holds *progress*, not an action — "I want to filter / assign / export…" is a task and fails the
      disqualifier. Use a progress verb (free me / help me / give me / take away / equip me / so I can…).
- [ ] **Right altitude.** Sits on the rung the user committed to — not the near-task rung, not the cosmic one.

## Axis 2 — GROUNDING (often invisible from the text)

- [ ] **Push present and real.** There's an actual struggling moment, not a mild inconvenience.
- [ ] **Push + pull both present.** Demand needs both; a pull with no push (or vice versa) is not yet a job.
- [ ] **Evidence basis stated.** Where does this come from — observed customer behavior, or assertion?
- [ ] **Confidence stamped.** Strong / Moderate / Directional / Hypothesis, with one line of basis.
- [ ] **Hypothesis flagged if armchair.** If built on assertions, it's labelled **Hypothesis** with a
      named validation step (default: "find a customer who switched from [replaced solution]").

In REVIEW, you usually can't see grounding from a pasted statement — so flag *"unverifiable from the
statement — needs grounding"* rather than guessing. A statement can pass FORM completely and still be
ungrounded. Say both things separately; never average them into one score.

## Verdict shapes

- **CREATE converged:** all FORM gates green + altitude committed + confidence stamped. (Grounding gates
  may legitimately resolve to "Hypothesis" — that's a pass with an honest stamp, not a fail.)
- **REVIEW per statement:** `FORM: pass/fail (which gates)` + `GROUNDING: stated / unverifiable` +
  one-line verdict + a concrete rewrite if FORM failed.

## Common failures → what they actually are

- "...so they can quickly filter the results" → **task** (visualizable action). Climb to the progress
  the filtering serves.
- "...wants the dashboard to show X" → **feature-as-job** (names a solution). Ask what progress the
  dashboard delivers.
- "Busy parents want..." → **persona anchor.** Strip the demographic; put the weight on the situation.
- "The emotional job is to feel secure" → **job-typing.** Drop the type label; fold the emotion into the
  single job.
- A clean statement with no hint of what it replaces → **missing switch.** Rework until the fired
  solution is visible.
